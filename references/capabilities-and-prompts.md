# 内置流程：不依赖额外 Skill

组件执行提示：阅读 components-and-maps.md，直接复用包内组件和地图生成器。目的地研究改变主题变量、标题、装饰和内容。先生成、实际打开并检查，修复后给用户预览；不要把检查城市名、重复收起按钮、奇数天数、地图方位的工作交给用户。查不到素材时用内置交通图形与菜品占位，查不到坐标时不绘制伪地理图。地区轮廓可独立离线显示，精确街道和导航取决于外部资料。

先检查宿主提供什么工具，而不是用户安装了哪些 Skill。工具是执行能力，Skill 是操作指引。不要为了基础产物要求安装 agent-reach、设计技能或生图技能。下面的提示可由宿主助手直接执行，或传给当前环境的可用工具。

## 能力降级

| 能力 | 首选 | 缺失时 |
|---|---|---|
| 地点与文化检索 | 宿主联网搜索/官方网页 | 使用用户资料，区分审美联想和未经核实事实；先交付可更新路书 |
| 小红书/点评 | 已授权平台工具；公开网页索引 | 普通联网搜索，不伪造“已读原帖”；找不到店铺 URL 时提供标明为搜索的入口 |
| 食物/人物图片 | 有许可的网络图片或宿主生图工具 | 内置中性矢量/图标与清晰标签，不要求 API Key；不得冒充实拍 |
| 地图 | 地点所属国家/地区匹配的导航入口；授权底图 | 经纬度轮廓与路线，注明精度；不能错摆城市 |
| 本地网页 | 内置 Python 生成器与模板 | 助手按模板直接生成自包含 HTML；缺少运行时只说明当前环境限制，不指导用户安装整串技能 |

宿主没有联网或生图工具时，提示词不能创造这些工具。不要承诺完全相同的研究和出图结果；仍交付可用页面，标明待核实与示意素材。后续工具可用再替换相关数据/资产，不重建整页。

## 主题设计提示

实现参数：将研究结果写入 trip.json 的 visualTheme.palette（bg、surface、ink、muted、line、accent、accent-soft 七个十六进制色值），visualTheme.basis 保存来源和设计推断。通用生成器内置长行程列表、就地抽屉、一致的表面色和可读的文字首页，不依赖额外设计 Skill。displayTitle/visualLine 设置标题，themeLabel 设置眉题；可用项目内 titleArt 作完整装饰图，不切割成作者原来的逐字动效。destinationTheme=thailand-summer 是附带的泰国验证主题，素材和 geographicMap 可选；其他城市使用 visualTheme，并由助手围绕意象完成标题和装饰。缺研究能力时用中性主题，不冒充目的地研究完成。

你是旅行路书的设计者。输入：用户计划、城市、实际景点、主要交通、审美词。先提取旅途共同意象，再通过可用联网工具检索官方旅游机构/地标资料；用用户审美词表达氛围，不宣称是当地唯一风格。输出主题名、7 个色值、文字层级、首页构图、唯一的装饰/动效重点及其依据。功能结构完整保留，视觉主题随目的地改变。允许华丽标题，但不要强制逐字动效。5 天以上用紧凑列表或分组时间轴，活动日导航单行滚动，预览紧贴被点日期展开。形成一个精修默认版本，让用户只需补内容，避免多轮修 UI。检查 320/390/1440 宽度、奇数天数、14 天、长城市名、未知信息与减少动效。

## 今日吃什么检索提示

根据每一天的城市、实际景点/酒店位置、交通时间窗口和饮食偏好，查找 1—2 个顺路餐饮建议。先用已可用的小红书/大众点评读取能力；没有就立即转宿主联网搜索，优先餐厅官方、当地旅游机构或可信餐饮指南，必要时补平台公开索引。不要把无法读取原帖变成不可检索。

每个结果给出：菜品、推荐理由、店名/分店/地址、与行程的关联、来源 URL 和查验日期、图片及类型（实拍/授权/AI 示意）、地图入口、已核实的点评/小红书链接。没有路线地点时只能称“本城备选”，不能称“顺路”。预算、营业时间、交通方式和评分不推测。有过敏/忌口遵守已知信息。

平台店铺/笔记链接找不到时，保留一个明确标为搜索的入口，不能生成不存在的店铺 ID 或笔记链接。只找到地方菜品资料时，菜品可推荐但具体店待确认。输入变更后重新检查餐馆城市、餐段与绕行，不把旧城市推荐残留到新城市。

## 食物生成提示

生成 [菜品] 的路书卡片示意图，[本次主题] 配色，构图简洁，食物占主要画面，留安全边距。不得生成店招、店内环境、价格或榜单徽章。图片只能标为 AI 菜品示意，不能称为 [餐厅] 实拍。网络图片则记录许可与来源；无可用图片时用内置图形，保留完整推荐文字。

## 交通角色生成与检查提示

参考用户的 [角色] 与 [交通工具]，生成统一风格、透明背景、朝向一致的单独素材或 atlas。每个 atlas 单元内部至少留 12% 透明边距，不得跨单元。保留机翼、车轮和自行车辐条，清除杂边、其他格子的碎片、白底/黑底残留和游离像素。先在浅色与深色背景检查，再接入地图。按每段用户说的交通 mode 自动切换，不能让最终使用者选择装饰图片；待定插画按 components-and-maps.md 沿用已知方式，原始 mode 保持 unknown。镜像要根据路径切线与素材原始朝向，角色保持直立。

## 地图地区规则

先执行 map-navigation.md 的地点身份核对和备用规则。关键词URL只是未绑定地点的降级路径；已核实地点使用POI ID / Place ID直接打开，地图登记名与订单地址分开保留，不拼长备注搜索。

导航服务按每个地点所属国家/地区选择：中国大陆默认高德，境外默认 Google Maps；允许用户覆盖。混合跨国行程不能用一个全局地图服务覆盖所有地点。Google 搜索用 https://www.google.com/maps/search/?api=1&query=（正确编码的地点与城市）；高德用 https://uri.amap.com/search?keyword=（正确编码的地点）&city=（城市）&view=list。不会提供密钥给这些 URL。导航服务与页面底图是两个配置，不能把使用 Google 导航说成已接入 Google 底图。

## 交付质量提示

从用户角度打开完整网页：每个被点日期下方是否直接展开；再次点击是否收起；活动项是否可见；地图每段是否连接、换乘角色是否自动改变、方位是否正确；推荐能否查地图/店铺/来源/平台；每日正文和美食是否属于同一个表面色系统。用深色强调重点，普通区域不出现莫名绿块/多层底色。检查真实下载文件及未知日期状态。修好这些再交付，不把 UI 检查留给用户。

每张预览都要有真实或明确暂拟的当天小总结和统一图标，有足够内容再提炼短主题；检查文字完全落在所属卡片内，长列表禁止压缩卡片高度。查看完整订单而不只是统计：用户给出的日期、时区、班次、房型、金额与规则不得丢失，待付款与取消不误写已确认，原有预订与行程冲突不能静默删除。采用 preview-motion-and-orders.md 和内置组件，逐帧检查切换收尾，真实触摸检查中断；把结果和未验证环境写清楚。
